Established 2026-07-04 (issue #120 work); observer machinery hardened 2026-07-12 (issue #183). Verified green on the iOS 26 simulator toolchain.

- **`key-preview-balloon` identifier exists kit-side** (`KeyPreviewBalloon` in `IPAKeyboardKit/UI/KeyboardView.swift`): a single *unlabeled* accessibility element (`.accessibilityElement(children: .ignore)` + identifier), present exactly while an insert key is pressed on iPhone (never on iPad — `KeyButton.showsPreviewBalloon`; balloon tests `XCTSkip` on non-phone idiom). Before #120 it was `.accessibilityHidden(true)`, which removes an element from the XCUITest tree entirely — a hidden element is NOT queryable, so making transient UI assertable requires replacing hidden(true) with an unlabeled element, not adding an identifier alongside it.
- **XCUIAutomation thread rules on this toolchain (empirical, load-bearing):** event *synthesis* (`press(forDuration:)` etc.) from a non-main thread raises `NSInternalInconsistencyException` "Must be called on the main thread" — the background-gesture-plus-main-thread-assert pattern from older blog lore is DEAD here. So mid-press assertion of transient UI = gesture on main (blocking) + background observer thread polling. Helper `observe(whilePerforming:poll:)` in AlternatesPopupUITests.swift: `OSAllocatedUnfairLock` state, 0.1 s poll cadence, stops at first `true`, always joins (expectation + `wait`) before returning so no orphaned polls survive into the next gesture/failure/teardown. 10 s hold (`pressHoldDuration`) gives issue-#96-scale poll-inflation margin.
- **Background polls must NOT run element queries — AND per-poll `snapshotWithError:` is NOT safe either** (crashes: CI runs 28731666930/PR #135 and 29002513638/issue #183). Mechanism, established by disassembly of Xcode 26's XCUIAutomation: XCUI auto-activities ("Find the %@", "Checking existence of …") are run through the **device's shared `reportingContext`** (`-[XCUIElement resolveOrRaiseTestFailure:error:]` → `runInternalActivityNamed:block:`), not a thread-local XCTContext — so records created from a bare observer thread attach to whatever record is current on the test thread (the gesture's transient activity during `observe`), and a poll straddling its completion trips `XCActivityRecord _ensureValid`. Per-poll `snapshotWithError:` still re-resolves the app element every call (the crash log's `t = nans` "Find the Target Application" lines) — it only narrowed the window. Wrapping the observe window in an outer `XCTContext.runActivity` would NOT fix it (polls attach to the *innermost current* record in the shared context, still the gesture's). The airtight fix (issue #183): `AppSnapshotSource` in AlternatesPopupUITests.swift pre-resolves `app.accessibilityElement` (`XCAccessibilityElement`, a pid token) + `device.accessibilityInterface` (`XCAXClient_iOS`) once on the test thread before the gesture; each poll calls `requestSnapshotForElement:attributes:parameters:error:` directly via IMP cast (4 args exceed `perform`'s limit) — verified by disassembly to emit zero activities (only os_log + a reply-future wait). nil attributes → `XCAXDefaultStringAttributes_iOS` (includes `identifier`); nil parameters → `defaultParameters`; returns `XCUIElementSnapshotRequestResult`, whose `rootElementSnapshot` casts to `XCUIElementSnapshot` for the same children/identifier walk. (A defaults key `XCTDisableSnapshottingForEventsOnApplication` gates app re-resolution globally — rejected as blunter than scoping the fix to the poller.) Raw snapshots DO respect `.accessibilityHidden` (verified: the pre-popup hidden alternates overlay never shows up).
- **Accessibility-tree exposure trails the render by ~0.1–0.3 s per element, independently** (measured at ~0.2 s sample spacing): two elements flipped by the same SwiftUI state change can overlap for one sample in the AX tree (the balloon-vs-popup test tolerates exactly one overlap sample; a real stuck overlay persists the whole hold), and a briefly-shown element can miss the AX tree entirely (the balloon's 0.3 s pre-popup showing routinely never appears in samples).
- **Cap-release commit** (PR #107 behavior): a stationary element-targeted `press(forDuration: 0.8)` on a key *with* alternates releases on the cap's center → types the base symbol exactly once. Asserted in the editor scratchpad via a label-predicate-scoped query (`identifier == layout-editor-scratch AND label == "ɹ"` + `waitForExistence`) — the bare `scratch.label` snapshot right after the press can race the SwiftUI re-render. Exactly-once falls out of exact label equality ("ɹɹ" on double emission).
- The frame-settle loop from the slide-to-popup test is now the shared `waitForStableFrame(of:)` helper; `openEditorPreviewRhotic()` is the shared launch→detail→editor arrange used by both scratchpad tests. See [[project_uitest_baseline]] for the preview-key identifier scheme (`key-insert-<text>`).
